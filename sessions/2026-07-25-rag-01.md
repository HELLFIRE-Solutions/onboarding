## Phase 2 — Architecture decisions (done — but material lives somewhere the template didn't anticipate)

**Finding before the decisions themselves:** rag-01 has **no `docs/` directory at all** — not "docs/architecture.md renamed" (gtm-agent) and not "docs/standard.md + sub-docs" (compliance-layer), but decisions folded directly into `README.md`. A third variant of "where architecture decisions live," not covered by the template's "if it exists" hedge on `docs/architecture.md`. See template update below.

Three decisions worth explaining without looking them up:
1. **pgvector over Qdrant** — self-hosted extension on the same shared Postgres instance, not a standalone vector-DB service. Reason: the droplet is 1 vCPU/~1.9GB shared with TETA+PI; `internal-db` already committed to "schema-per-concern in one Postgres" for exactly that RAM constraint, and TETA+PI's own `tetapi-postgres` already proves `pgvector/pgvector:pg16` works on this box. Qdrant would be a second full process on an already-tight machine.
2. **Local embeddings by default** (`fastembed`/ONNX, no PyTorch, 384 dims) — no data ever leaves the machine, strongest DSGVO position; `MistralEmbedder` (EU company) is the fallback only if local inference proves too heavy on the shared droplet.
3. **Chunking + shared interface** — headings first, then paragraph-split for headingless/long blocks; deliberately reuses the exact `RawChunk(source, heading, text)` shape office-agent's BM25 stub already uses, so office-agent can swap in this pipeline later without changing its own ingest→chunks→search contract.


Both ran clean from `README.md` alone, no external accounts, no hints — verified live in this session. **But:** unlike gtm-agent (where the test suite mocked the one external dependency, the Claude API, and the CLI itself ran end-to-end on sample data without it), rag-01's test suite only exercises `LocalVectorStore` (in-memory numpy). `rag/cli.py`'s `_store()` unconditionally returns `PgVectorStore` and raises if `RAG_DATABASE_URL` isn't set — **there is no dev/offline fallback in the CLI itself.** A green `pytest` run here proves the chunking and ranking logic is correct; it proves nothing about the actual `rag ingest`/`rag query` path, because that path structurally requires Postgres+pgvector.

This machine has neither `docker` nor `psql` installed, so the real CLI path couldn't be run in this session — but this is a **different kind of blocker** than gtm-agent's HubSpot/domain gap. gtm-agent was blocked on a resource that didn't exist anywhere yet. Here, per `STATE.md`, the actual dependency (the `rag` schema, `CREATE EXTENSION vector`, `rag.chunks` with its HNSW index) **was already applied for real** against the shared droplet's Postgres on 2026-07-24 — it exists in production, it's just not reproducible on this particular onboarding machine. Conflating "not deployed yet" with "deployed but not locally testable" would be a mistake — check `STATE.md` before treating a DB-dependent module as blocked.

## Phase 5 — Guardrails and limits (adapted — infra modules don't have "refuses to act" guardrails)

Neither gtm-agent's "refuses to draft without X" nor compliance-layer's "explicit non-goals" language maps cleanly here — rag-01 doesn't act on anyone's behalf (no send, no draft, nothing for a human to approve), so there's nothing to gate that way. What actually plays the guardrail role for an infra module:
- **Fails loud, not silent:** `PgVectorStore.__init__`/`_store()` raise immediately if `RAG_DATABASE_URL` is missing — no silent fallback to an ephemeral in-memory store in what would be a production path.
- **No automatic/scheduled ingestion** — `rag ingest`/`rag query` only run on explicit invocation; nothing indexes data on a timer or on file-change.
- **Data residency by construction** — the default embedder never sends text off-machine; the Mistral fallback is explicitly framed as a fallback, not the default, specifically to preserve that position.
- Explicitly **not done yet**: hybrid BM25+dense retrieval (Stage 2), production deploy of the CLI against the real droplet DB from a client machine, the `rag_app` scoped Postgres role (flagged in `STATE.md` as owned by this session, still open).
